## 2. Manual ad-Cost entry corrupted live data twice — now guarded (`3c73958`, `4ad7f4a`)

Ads Manager reports **the selected date range**. `POST /api/advertising/manual` takes **one day**, and a newer observation silently replaces the previous one. On 2026-09-01 that misfired twice within an hour:

| time | entered | dashboard then showed |
|---|---|---|
| 21:28 | `2000`, sku_orders 0, gross 0 | **+414,200 profit, +62% margin** |
| 22:08 | `5,062,670 / 87 orders / 8,636,752` | **−4,646,470, −697% margin** |

The second is plainly a month's figures — that day the shop did 8 orders, 10 units, 825,000 GMV. Both restored by re-posting the real day; superseded `SourceReport` rows stay in the audit trail, so nothing was lost.

**Current, correct state for 2026-09-01:** Cost `450,000`, sku_orders `10`, gross `810,904` → **net −33,800, margin −5.07%**, still `partial` (day open).

**The guard, as built** (`3c73958`, holes closed in `dac5cce` and the round-2 commit, after two review rounds).
`record_manual_ad_day()` runs **three** deterministic checks against facts already in the database,
each raising `NeedsConfirmation` → 422 `{"detail": {"message", "confirmable": true}}`:

1. entered `sku_orders` or `gross_revenue` over **2×** the day's own `analytics_shop_daily` units / GMV
   → *"these look like period totals, not one day"*. `PERIOD_TOTAL_FACTOR` in `src/domain/reports.py`.
   **Stands down while the day's actuals are still zero** — Ads Manager legitimately runs ahead of the
   hourly order sync, so comparing against zero would refuse every early entry. Deliberate: these two
   are reported figures no profit line reads. The field that moves net profit is Cost, covered by (2).
2. Cost over **4×** the median of the last **14 days with spend** before this day (`COST_SPIKE_FACTOR`,
   `COST_SPIKE_WINDOW`, min `COST_SPIKE_MIN_DAYS` = 5). Reads only `shop_ad_days`, so it works the
   moment a day opens, before any order has synced — this is the check that covers a period's Cost
   entered as the **first** entry of a day with the other fields left blank. Zero-spend days are
   excluded **in SQL, before the limit**, so a pause in advertising cannot empty the window and
   disarm it on the resume day. On live data 2026-09-01: median 219,616 → threshold **878,464**; the
   month's 5,062,670 is caught, the real 450,000 passes.
3. a cost **below half** the one it would replace, or a record that blanks `sku_orders` /
   `gross_revenue` that were non-zero → *"this would overwrite a fuller record"*. `COST_DROP_FACTOR`.

**Omitted ≠ zero.** `sku_orders` and `gross_revenue` are nullable end to end: omitting one means
*leave the day's existing figure alone*; blanking requires typing `0`. Without this the form's own
post-apply clearing made the second entry of a day resubmit zeros — and the only remedy offered,
"Save as entered", performed exactly the blanking the guard exists to prevent. An inherited figure is
recorded in the payload as `carried_over: [...]`, because under `final=True` it silently becomes the
day's closing number without having been read off the screen again. The inputs show
*«оставить <текущее>»*, falling back to *«не менять»* when the entry date lies outside the selected
period and no record is at hand to quote.

Neither is silent and neither is final: `confirm=true` saves the figures as entered and is written into
the report payload as `confirmed_override`, so an override stays in the audit trail. A day with no
actuals yet cannot trip check 1, so a first entry is never blocked.

The form now states its single-day scope twice (a pill in the header, a line beneath it), shows
**«Всё равно сохранить»** only after a confirmable refusal, and withdraws that button the moment any
field is edited — you can only confirm the exact figures the server objected to.

Error parsing moved to `apps/dashboard/src/lib/errors.ts` (React-free, hence unit-testable) and
`ApiError` carries `confirmable`. The MOCK route mirrors checks 2 and 3 on the same 14-day window;
check 1 needs per-day analytics the fixtures have no equivalent of, so it is backend-only and marked
as such in the route. **The fixture holds only 5 days with spend, so the MOCK cannot exercise check 2
at all** — its coverage is the backend unit tests and the production smoke test, not the dev server.

**Verified on production** after deploy — both of the day's real incidents now bounce, day untouched:

| replayed against live prod | result |
|---|---|
| `5,062,670 / 87 / 8,636,752` | 422 *"SKU orders 87 is over 2x the 10 units the shop actually sold on 2026-09-01…"* |
| `2000 / 0 / 0` | 422 *"Cost 2000 is far below the 450000 already recorded for 2026-09-01…"* |
| real day `450,000 / 10 / 810,904` | 201, day stays `450000 / 10 / 810904`, net −33,800 |

Do **not** "solve" this by splitting a range across days. Allocating a period's Cost per day is an invented number, which SPEC §2 and `CLAUDE.md` forbid outright.

## 4. Infra: the repo moved off iCloud — `~/Desktop/TT` → `~/dev/TT`

`~/Desktop` is iCloud-synced, and it was actively syncing `apps/dashboard/node_modules` (~180 MB, tens of thousands of files). Symptoms it caused: `next dev` bound its port but never answered a request; `npm run build` failed with `ENOTEMPTY`/`ENOENT` and needed 2–3 attempts; copying `node_modules` off Desktop ran at ~100 KB / 20 s. Worst of all, **`.git/refs/heads/main` was missing**, left as an unrenamed `main.lock`, so every git command answered *"branch main does not have any commits yet"* — recovered by renaming the lock back to the ref (the sha inside was correct and the object intact).

After the move: `npm ci` 9 s, `next dev` ready in 2.3 s, `npm run build` green on the first attempt in 33 s.

**Other projects are still on `~/Desktop` (BUBU, Jony, PS_2026, Gefest…) and carry the same risk.** Before moving one: delete `node_modules` / `.venv` / `.next` first, or `mv` spends hours re-downloading cloud-evicted files.

## 9. Reference: API contracts for the two entry features

**`POST /api/advertising/manual`** `{date, cost: string, sku_orders, gross_revenue: string, final: bool, note}` → 201 `{report_id, partial, unchanged?, recomputed:{orders, inserted}, day:{...}}`; 422 with a `detail` string (newer entry exists / future date / final on an unfinished day). Only a *newer* observation may replace a day; `final=true` closes it. `shop_ad_days.manual` marks per-order snapshots `ad_source=manual_entry_cost` rather than `campaign_overview_cost`.

**`GET /api/advertising?from&to`** → `{cost, known_cost, gmv_pay, covered_days, expected_days, missing_days[], partial_days[], status, source, manual_days, entry_note, reports[], days[]}`; `days[].source` is `"shop_overview" | "manual_entry"`. Also embedded as `overview.advertising`.

**`GET /api/costs?from&to`** → `{default_cogs_per_unit, lots[], skus[], note}`.
`lots[]`: `{id, scope "all"|"product"|"sku", product_id, sku_id, received_on, unit_cost, quantity|null, currency, note, active, consumed?, remaining?, shared_skus?}`.
`skus[]`: `{sku_id, external_sku_id, product_id, product_title, sku_title, current_cost, source "lot"|"seed"|"default"|"none", lot_id, effective_from, history[]}`.
Writes: `POST /api/costs/default`, `POST /api/costs/lots` (201), `PATCH /api/costs/lots/{id}` (`quantity: 0` clears to "until next lot"). Every write rebuilds FIFO versions, recomputes profit and aggregates synchronously, and returns `recomputed:{orders, inserted}`.

**FIFO semantics** (`src/domain/costs.py`): a `scope=all`/`scope=product` lot's `quantity` is one shared purchase batch, consumed against the **combined** sales of every SKU it covers, not per SKU. A lot without a quantity applies until the next one. A SKU's seed/manual cost still covers the time genuinely before its first lot. The worker rebuilds versions at the top of every `_compute_profit()`, otherwise lots freeze once exhausted.
