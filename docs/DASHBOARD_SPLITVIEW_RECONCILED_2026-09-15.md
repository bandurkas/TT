# Split View для z3b/z4b — согласование ТЗ v2.1 с реальностью

Источник: `deepseek_markdown_20260915_9b0aa1.md` (ТЗ v2.1, редизайн дашборда).
Решено с владельцем: **архитектуру не трогаем** (single-page, якорная навигация,
зоны z1…z7 из `Shell.tsx`), **Split View добавляем поверх** зон «Товары» (часть z3b /
Explorer products) и «Видео-креативы» (z4b), вместо модалки `VideoTrigger`.
Технологии — только то, что уже есть: Next.js 15 / React 19 / TS, без UI-kit,
без чарт-библиотек, самописный SVG (см. `SplitChart` в `VideoProducts.tsx`).

## 1. Из ТЗ забираем как есть

- Паттерн Split View: список 40% слева / фокус-панель 60% справа, клик или ↑↓
  мгновенно переключает фокус, без модалок и переходов (разд. 6.2, 9, 10).
- KPI-строка сверху зоны, клик по плитке — сортировка списка (разд. 10.4).
- Прогрессивное раскрытие снизу вверх в фокус-панели.
- Активная карточка — цветная полоса + подсветка, клавиатура ↑↓ (разд. 9.3, 10.5).
- Цветовая кодировка `net_margin` по величине — но 3 тона (`--good`/`--warn`/`--bad`,
  уже есть в токенах), не 4: своего "тёмно-красного" токена в приложении нет, а
  заводить его ради одного компонента — лишняя сущность. ≥15% good, 0–15% warn,
  отрицательная bad; `null` — без тона (см. §3).
- Брейкпоинты и поведение на мобиле/таблете (разд. 5, 18) — переносим без Drawer:
  список сверху, фокус снизу, свайп между карточками.
- Тултипы с формулами у метрик (разд. 3, пункт 8) — обязательны, т.к. дальше
  вводим Reported/Adjusted разницу, которую пользователю нужно объяснять.

## 2. Что не переносим и почему

| Из ТЗ | Причина отказа |
|---|---|
| 8 экранов (SCR-001…008) + левый Drawer | Уже отклонено владельцем — остаёмся на single-page/якорях |
| 35-компонентная дизайн-система + Storybook | Нет ни одной сторонней UI/чарт-библиотеки в `package.json`; это новая инфраструктура, а не редизайн. Проект живёт минимальными диффами (`CLAUDE.md`) |
| Tailwind | Не используется, весь стиль — `globals.css` |
| Hook Rate / Hold Rate / график отвала по секундам (разд. 10.6.2–10.6.3) | Нет подтверждённых полей (`p25/p50/p75/p100`, `watch_time`) в `docs/tiktok-api-capability-matrix.md`. По правилу проекта «недоступное поле = NOT AVAILABLE, не костыль» — нельзя рисовать эти метрики, пока поле не подтверждено в API и не добавлено в adapter |
| ROAS/CPA/Расход в фокус-панели видео (разд. 10.6.2) | `VideoCard.ad_spend` и `VideoCard.net_profit` в `lib/types.ts` **буквально типизированы как `null`** — атрибуция рекламы на уровне видео не реализована. Показывать выдуманные числа нельзя |
| Демография зрителей, A/B-сравнение (разд. 10.6.7–10.6.8) | Нет полей в `VideoCard`/`Videos`, нет упоминания в SPEC.md. Не в этой фазе |
| Единый ROAS/маржа без пометки (разд. 21.1–21.2) | Прямое нарушение `CLAUDE.md`: «Reported ROAS ≠ adjusted/blended — всегда подписывать»; SPEC.md §7 требует хранить `reported_roas`, `adjusted_roas`, `blended_gmv` раздельно |
| 3 месяца / отдельные этапы аудита-Figma-QA (разд. 24) | Не соответствует темпу проекта (Phase 1 сделан за день). План ниже — по факту |

## 3. Финансовая модель — обязательные поправки

Реальные поля (`lib/types.ts`) вместо формул ТЗ разд. 21:

**Товар (`ProductRow`)**: `gmv`, `net_seller_revenue`, `fees`, `affiliate`, `cogs`,
`ad_cost` (nullable) + `ad_cost_is_estimate: boolean`, `refunds`, `net_profit`
(nullable), `net_margin` (nullable), `cvr`, `ctr`, `status` + `status_reason`.

**Видео (`VideoCard`)**: `views`, `impressions`, `clicks`, `orders`, `gmv`, `ctr`,
`cvr`, `gpm`, `ad_spend: null`, `net_profit: null`, `classification` (`VideoClass`),
`confidence` (HIGH/MEDIUM/LOW), `reasons: string[]`, `age_days`, `duration_seconds`.

Правила отображения:

1. **`ad_cost_is_estimate === true`** → визуально помечать (например, «≈» перед
   суммой + сноска «оценка распределения, не факт»), не показывать как точное число.
2. **`net_profit === null` / `net_margin === null`** → состояние «не рассчитано»,
   не `0` и не прочерк без объяснения — это разные вещи (0 прибыли ≠ нет данных).
3. **Видео: `ad_spend`/`net_profit` всегда `null` сегодня** → в фокус-панели видео
   блок «Реклама и прибыль» показывает `ad_spend_note` из API (уже есть готовое
   текстовое объяснение почему нет данных) вместо KPI-плиток с цифрами.
4. **`classification` + `confidence` + `reasons[]`** — этого нет в ТЗ вообще, но
   это ядро ценности проекта (evidence + confidence по `CLAUDE.md`). Обязательно
   в фокус-панель, на видном месте — сильнее, чем просто "ROAS ↑/↓" из ТЗ.
5. Если/когда появится `reported_roas`/`adjusted_roas`/`blended_gmv` на дашборде
   (сейчас, по HANDOFF, есть только по кампаниям, не сведено к периоду) —
   показывать оба числа рядом с явной подписью, никогда одно без другой.

## 4. Фокус-панель «Товар» (расширение z3b/Explorer products)

Из реально доступных полей:
```
[фото недоступно — нет поля в ProductRow] Название · SKU (external_product_id)
──────────────────────────────────────────
GMV · Net seller revenue · Заказы · Юниты
Fees · Affiliate · COGS · Ad cost (≈ если estimate) · Возвраты
Net profit (или "не рассчитано") · Net margin (цвет по величине)
CTR · CVR
Статус (ProductStatus) + status_reason — текстом, не только бейджем
```
Список слева — переиспользует текущие столбцы `Performers.tsx`
(`bestProducts`/`worstProducts`), просто с фокус-панелью справа вместо
раздельных best/worst таблиц.

## 5. Фокус-панель «Видео» (замена модалки в z4b)

```
[встроенный плеер вместо VideoTrigger-модалки — video_reference]
Подпись (caption) · возраст крео (age_days) · длительность
──────────────────────────────────────────
Impressions · Clicks · CTR · Views · Orders · GMV · CVR · GPM
──────────────────────────────────────────
Classification (WINNER/LOSER/FATIGUING/…) · Confidence · Reasons[] ← разворачиваемый список
──────────────────────────────────────────
Реклама и прибыль: "Не рассчитывается на уровне видео — {ad_spend_note}"
──────────────────────────────────────────
Товары, которые продаёт это видео (переиспользовать блок из VideoProducts.tsx)
```

`VideoTrigger` не выбрасываем — он остаётся способом открыть видео из мест вне
z3b/z4b (например, из таблиц `Explorer`). Внутри Split View плеер встроен
постоянно в фокус-панель, не модалкой.

## 6. Layout

Переиспользуем существующие классы (`.zone`, `.card`, `.two`, `.scroll`, `ZoneHeader`,
`Pill`/`ProductPill`/`VideoPill`, `Skeleton`, `ErrorNote`, `useT`/`useLang`,
`idr`/`int`/`pct`/`num`). Новый CSS: `.split` (grid 40/60, `@media` схлопывание
в 1 колонку < 760px, как уже сделано для `.rail` в `Shell.tsx`).

## 7. Фазы (по факту темпа проекта, не 3 месяца)

1. **Split View «Товары»** — список + фокус-панель, только существующие поля.
   Минимальный диф, переиспользует `performers.ts`.
2. **Split View «Видео»** — фокус-панель с встроенным плеером, classification/
   confidence/reasons на видном месте, явный "не рассчитано" для рекламы.
3. **Проверка API** (отдельно, до кода): есть ли у TikTok video-quartile/watch-time
   поля вообще — если да, добавить в adapter + `docs/tiktok-api-capability-matrix.md`
   по правилам SPEC.md, только потом Hook/Hold Rate на дашборде.
4. **Reported/Adjusted/Blended к периоду** — блокер по HANDOFF §3: нужна миграция
   `analytics_shop_daily`, без неё нельзя честно показать ROAS периода нигде,
   включая новые Split View.

Каждая фаза — по флоу `CLAUDE.md`: план → минимальный диф → тесты → независимое
ревью → деплой → live-check. Ничего не мержим без явного шага ревью (в HANDOFF
2026-09-15 §2 отмечено, что два раунда ревью по текущей рекламной работе ещё не
проводились — долг, не пример для новых диффов).
